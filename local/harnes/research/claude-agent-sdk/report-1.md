**Verdict: No.** The Claude Agent SDK starts or resumes a *conversation* by session ID; it has no API that attaches to and steers an already-running `claude` CLI/Code process. The only official way to drive a live local session is Remote Control, a claude.ai/mobile surface with no SDK/API.

Sources read 2026-09-15 (UTC): platform.claude.com/docs/en/agent-sdk/{overview,sessions,streaming-vs-single-mode,typescript,hosting}; code.claude.com/docs/en/remote-control; code.claude.com/docs/en/cross-session-messaging. Repo `8f86d7ca99b0af94fd4ec7653d76d84f84079c40`, `src/wrapper.ts`, `src/commands/spawn.ts`, `src/stream.ts`.

- **FACT — what the SDK is.** "The Agent SDK gives you the same tools, agent loop, and context management that power Claude Code, programmable in Python and TypeScript" (overview). It is a library that runs the loop for you; to drive it from another language, "run the CLI as a subprocess with the `-p` flag and `--output-format json`."
- **FACT — start and resume only.** `Options` exposes `continue: boolean` ("Continue the most recent conversation"), `resume: string` ("Session ID to resume"), `forkSession`, `persistSession`, `sessionStore`, plus `spawnClaudeCodeProcess`/`pathToClaudeCodeExecutable` for *how the SDK spawns its own* CLI (typescript). There is no attach/connect/control option. "Resume takes a specific session ID."
- **FACT — resume is transcript replay, not process attach.** "Session files are local to the machine that created them" and live under `~/.claude/projects/<encoded-cwd>/*.jsonl` (sessions). Cross-host resume is done by mirroring transcripts with a `SessionStore`, not by reaching a running process.
- **FACT — events and follow-ups are within the SDK's own process.** Streaming input is "a persistent, interactive session" where you "send multiple messages that process sequentially" via `streamInput()`; real-time events stream from the SDK-spawned CLI. Hosting doc: "Your application handles client requests on that port and calls the SDK internally; the subprocess itself does not listen on the network." So no inbound socket on a bare CLI exists to attach to.
- **FACT — the SDK's `reinitialize()` is not attach.** It "Re-sends the initialize control request to the running CLI ... Use it after a transport gap, such as reattaching to a session after a disconnect" (typescript). That is re-initializing the SDK's *own* spawned CLI after its transport dropped, not joining an unrelated running process.
- **FACT — the one official live-control path is Remote Control.** "Remote Control connects claude.ai/code or the Claude app ... to a Claude Code session running on your machine"; "A connected device shows the conversation in your terminal as it happens." Limits: Pro/Max/Team/Enterprise only ("API keys are not supported"), local process must keep running, "One remote session per interactive process", and traffic is stored on Anthropic servers. It is a human web/mobile client, not an SDK API. Cross-session messaging is Claude-to-Claude tool use (`SendMessage`/`ListAgents`), not programmatic attach.
- **FACT — fit with Limen/Herdr/CCS.** `src/wrapper.ts` runs `claude -p <task> --output-format stream-json ...` (start-only) and already persists the CLI `session_id` to `jobDir/claude-session` (`src/stream.ts`); `--continue`/`--session-id` resume is Pi-only, and `src/commands/spawn.ts` refuses hosted Herdr for `--engine claude`. So today Limen can start Claude and could later resume by ID, but cannot attach; Remote Control also cannot run under Limen's refused hosted-Claude path and would need a claude.ai-login CCS profile.
- **PROPOSAL — not worth building attach on the SDK; 1–3 no-code next steps.** (1) Decide whether the requirement is "attach to a running process" or "continue the same conversation"; only the former is impossible and the latter is `resume <id>`, for which Limen already has the ID. (2) If live steering from a program is truly required, treat it as a separate product question and prototype Remote Control manually on a spare CCS profile (a2/a3), accepting it is web/mobile/manual with no API. (3) If hosted programmatic multi-session control is the goal, evaluate Managed Agents — the overview calls it "Hosted REST API, a separate product from the Agent SDK" with session events/streaming — instead of the local CLI. **QUESTION:** which of the three is the actual need? That decides the next ticket.
